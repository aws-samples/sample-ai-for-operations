## Overview

The BYOC Infrastructure Discovery Agent is a read-only, programmatically-invoked
Amazon Bedrock (Strands) agent deployed as a single AWS Lambda (Python 3.12, ARM64).
It answers AWS region, availability zone, AMI, instance-type, and Amazon EKS metadata
queries — including for regions not enabled in the caller's account — by reading
account-independent public sources (AWS SSM global-infrastructure parameters, the
AWS Price List API) with live read-only EC2 `Describe*` calls as enrichment. It makes
**no mutating calls to any AWS environment**. The deployability verdict is computed
deterministically in code (`assemble.py` / `compute_deployability.py`), never by the LLM.

## Data Classification

| Data | Classification | Notes |
|------|----------------|-------|
| Region / AZ / AMI / instance-type / EKS metadata | Public | AWS global-infrastructure facts, published pricing |
| Curated data files (ENI max-pods, EKS ECR registries, S3 LocationConstraint, EKS EOL) | Public | Sourced from public AWS documentation |
| Invocation queries | Internal | Free-text queries from provisioning automation; no PII expected |
| CloudWatch logs | Internal | Structured JSON; never include prompts, responses, or query text |

No customer PII or secrets are processed or stored.

## Detailed Findings

### Spoofing

- **[MEDIUM] No authentication at the code or CDK layer** — Component: `src/handler.py`, `infra/lib/agent-stack.ts` (no ingress/authorizer) — Mitigation: The Lambda is invoked only via IAM-authenticated SDK calls (caller requires `lambda:InvokeFunction`); when fronted by API Gateway, IAM or Amazon Cognito authorization is required at the gateway. This is documented as a deployment prerequisite. The invocation boundary is intentionally defined outside this repository.
- **[LOW] Source identity of public data not cryptographically verified by the agent** — Component: `src/tools/_common.py`, `src/tools/resolve_*.py` — Mitigation: All source calls use the AWS SDK over TLS to AWS-owned endpoints with SigV4; there is no custom or plaintext HTTP. Every fact carries a `source` and `confidence`.

### Tampering

- **[MEDIUM] Prompt injection via the unvalidated query field** — Component: `src/handler.py` (`_extract_query`), `src/agent.py` (`gather_facts`), `src/prompts/system_prompt.md` — Mitigation: Blast radius is bounded by design — `compute_deployability` and `format_response` are excluded from the agent toolset so the LLM cannot set the verdict; model output is coerced through a pydantic schema (`GatheredFacts`) and the final contract is assembled deterministically in `assemble.py`. The system prompt forbids emitting facts from model knowledge. The Amazon Bedrock Guardrail created by the stack filters abusive input. It has no prompt-attack filter, so it is not a prompt-injection control.
- **[LOW] Path traversal via curated dataset name** — Component: `src/tools/lookup_curated_data.py` — Mitigation: The `dataset` argument is allowlisted against a fixed `_VALID_DATASETS` set before any filename is constructed; an invalid name returns a structured error.
- **[LOW] Stale or incorrect curated data files** — Component: `src/data/*.json` — Mitigation: Each dataset carries `_source` and `_last_updated` provenance (returned as `source_url` / `last_updated` with `confidence`), so consumers can see the data is curated. Files are version-controlled and reviewed.

### Repudiation

- **[LOW] No caller identity recorded in application logs** — Component: `src/logging_util.py`, `src/handler.py` — Mitigation: AWS CloudTrail records the invoking principal for `lambda:InvokeFunction`, and API Gateway access logs (when fronted) capture caller and request id. The agent handles only public data, so per-caller attribution is low value. The Lambda request id can optionally be added to log records.

### Information Disclosure

- **[LOW] Malformed-body parse error echoed into logs** — Component: `src/handler.py` (`bad_request` detail) — Mitigation: Only the JSON parse-error string is logged, never the query or model prompt/response. CloudWatch logs are access-controlled. The detail can be truncated if stricter handling is required.
- **[LOW] Stack traces or internal errors leaking to the caller** — Component: `src/handler.py` (broad `except`) — Mitigation: The handler catches all exceptions and returns a generic `internal_error` contract; only `type(exc).__name__` is logged — never a stack trace or message.
- **[LOW] CloudWatch logs encrypted only with an AWS-managed key** — Component: `infra/lib/agent-stack.ts` (`AgentLogGroup`) — Mitigation: Logs contain no PII, secrets, prompts, or responses, so AWS-managed encryption plus IAM access control is appropriate. A customer-managed KMS key can be attached if a compliance regime requires it.

### Denial of Service

- **[MEDIUM] No query size limit and no cap on agent tool-loop iterations** — Component: `src/handler.py`, `src/agent.py` — Mitigation: Each live AWS call fast-fails (3s connect / 5s read, max 2 attempts) and the Lambda has a hard 60s timeout and bounded memory, capping per-invocation cost. Lambda concurrency plus gateway auth/throttling bound aggregate volume. CloudWatch alarms fire on error rate > 5% and p99 latency > 30s.
- **[MEDIUM] Amazon Bedrock Guardrail is conditional and silently absent if env vars are unset** — Component: `src/agent.py` (`_build_model`), `src/config.py` — Mitigation: The CDK stack always creates the guardrail and injects both `GUARDRAIL_ID` and `GUARDRAIL_VERSION`, with no option to skip it, so every deployed stack is guarded. Residual risk is limited to running the agent outside the stack without both variables set.
- **[LOW] Upstream public-source unavailability (region not enabled / SCP denied)** — Component: `src/tools/_resilience.py` (`try_live`) — Mitigation: `try_live` swallows connection, opt-in, and denied errors and falls back to the account-independent global source, returning a usable answer with adjusted confidence rather than failing. Caching (in-memory + `/tmp`) reduces repeat calls.

### Elevation of Privilege

- **[LOW] Wildcard resources on read-only / telemetry actions** — Component: `infra/lib/agent-stack.ts` (`ReadPricing`, `DescribeReadOnlyEc2`, `XRayTracing`) — Mitigation: `pricing:GetProducts`, `ec2:Describe*`, and `xray:Put*` do not support resource-level scoping; all are read-only or telemetry (non-mutating). No wildcard exists on any write action. SSM, Amazon Bedrock, and Logs statements are ARN-scoped.
- **[LOW] Agent coerced into performing a mutating action** — Component: `infra/lib/agent-stack.ts` (execution role), `src/tools/*` — Mitigation: The execution role contains **no mutating actions whatsoever**; every tool is read-only. Even a fully hijacked LLM cannot mutate any environment because the IAM boundary denies it. No `MUTATING_ACTIONS.md` is required.
- **[LOW] Cross-request state leakage between concurrent invocations** — Component: `src/agent.py` (`_new_agent`) — Mitigation: A fresh `Agent` with empty history is built per invocation; only the stateless `BedrockModel` is cached. This isolation is explicit in `_new_agent`.

## Content Filtering (Amazon Bedrock Guardrails)

The CDK stack (`infra/lib/agent-stack.ts`) always creates an Amazon Bedrock
Guardrail and sets `GUARDRAIL_ID` and `GUARDRAIL_VERSION` on the function. There
is no option to skip it, so every deployed stack invokes the model through the
guardrail. The agent code (`src/agent.py`) attaches the guardrail only when both
variables are set, so running the agent outside the stack without them applies
no guardrail.

The guardrail configures content filters only (hate, insults, sexual, violence,
misconduct) at HIGH strength on input and output. It does not configure a
prompt-attack filter, denied topics, or a sensitive-information (PII) filter.
This agent handles only public infrastructure facts, so the content filters
primarily protect against abusive input. Add further policies before production
if your use case needs them (see "Scope and limitations" in `README.md`).

## Key Management

No customer-managed secrets are required for core operation. The agent calls AWS APIs
only under its IAM execution role. If future features introduce secrets, they MUST be
stored in AWS Secrets Manager and injected via environment variables — never hardcoded.

## IAM Permission Boundary

The default execution role is read-only for customer/vendor environments and grants
agent-internal permissions only (own log group, X-Ray telemetry, Amazon Bedrock invoke,
guardrail apply). There are no mutating tools; therefore no `MUTATING_ACTIONS.md` is
required. See `README.md` and `infra/policies/execution-role-policy.json` for the full policy.
